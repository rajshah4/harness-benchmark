# AWS long-project harness comparison

Date: 2026-08-24 UTC

## Bottom line

On these two medium projects, Pi was the fastest and used the fewest model calls and tokens. OpenCode completed both projects correctly, but took roughly twice Pi's time and model usage. OpenHands used the most model context and failed two hidden durability checks on the second project.

This is a small benchmark, not a universal harness ranking. Its value is that the model, starting files, task, verifier, machine, and token accounting were held constant.

## What made the harnesses different

Pi took fewer steps and sent less context on every step. Across the two projects, OpenCode made 1.62 times as many model calls as Pi, while OpenHands made 1.91 times as many. OpenCode also sent about 1.46 times as much context per call. OpenHands sent about 2.11 times as much.

Those effects compound. OpenCode sent 2.36 times Pi's input tokens and cost 2.16 times as much. OpenHands sent 4.03 times Pi's input tokens and cost 3.27 times as much.

The durable queue also exposed a quality difference. Pi and OpenCode passed all ten checks. OpenHands failed two edge cases:

- a stale worker tried to complete a job after another process cancelled it
- interrupted-job recovery left a job unavailable instead of returning it to a runnable state

The failed checks matter more than a token win or loss. A harness that stops with incomplete behavior has not achieved the same outcome.

## How tokens were measured

Every model request went through a local recording proxy on the clean AWS instance. The proxy stored the raw usage returned by the GLM-5.2 provider. We count:

- model calls: successful provider responses
- input tokens: all context processed by the provider, including cached context
- fresh input: input tokens minus cache reads
- output tokens: tokens generated by the model
- cost: recalculated consistently from provider usage

All six official cells had zero provider errors. Cache reads were present for every harness. The earlier OpenHands `cache_read=0` observation was therefore not reproduced in this clean run.

## What Laminar added

Laminar captured a complete trace for all six cells, which makes it useful for inspecting the order and content of model and tool actions. It is not the authoritative token counter in this experiment.

- OpenCode's Laminar token totals matched the provider ledger.
- Pi's Laminar trace omitted some input recorded by the provider ledger.
- OpenHands' Laminar trace disagreed more substantially and reported zero cache reads even though the provider reported a 94 percent cache-read rate.

The practical rule is simple: use Laminar to understand what the agent did, and use the provider ledger to compare tokens and cost.

## Reliability note

An earlier diagnostic Pi run stopped with a retry message while provider calls continued in the background. The clean rerun passed. That event is retained as reliability evidence but is excluded from the timing and token table above. Failed infrastructure attempts that never created a conversation are also excluded.

## Reproducibility

- Environment: temporary clean AWS EC2 instance, Agent Canvas 1.15.0, Agent Server 1.42.1
- Model: GLM-5.2 for all harnesses
- Harnesses: Pi ACP, native OpenHands, OpenCode ACP
- Repair feedback: disabled
- Verification: hidden behavioral checks, run after the agent stopped
- Raw result JSON: `runs/20260824-aws-long-projects-v2-*.json`
- Raw provider ledger: `ledgers/20260824-aws-long-projects-ledger.jsonl`
- Scrubbed Agent Canvas histories: `canvas-state/20260824-aws/`

The six copied result files and provider ledger were checksum-verified against the AWS originals.
